# 如何把大模型结构图画对

模型结构图需要同时满足两件事：**结构事实正确**，以及**图形表达清楚**。前者不能靠经验补全，后者不能只靠肉眼检查。

## 1. 先界定图的粒度

本项目画的是“模型总体结构 + 单层 Decoder Block + 关键子模块展开图”。通常保留以下内容即可：

- 输入、Token Embedding、重复的 Decoder Block、Final Norm、LM Head、输出；
- Block 内的 Norm、Attention、FFN / MoE、残差加法；
- 注意力类型与 FFN 类型；
- 层数、隐藏维度、头数、KV 头数、FFN 中间维度等关键尺寸；
- 每张总体模型图都必须从 Token Embedding 框以虚线引出 `Embedding dimension of …` 标注；数值以醒目颜色突出，并且来自结构规格；
- 只有在模型确实使用时才画的组件，例如 RoPE、滑窗注意力、线性注意力、MoE、Mamba / mixer、KV cache 等。

不要把实现级细节（权重初始化、dropout、每一个张量 reshape）全部塞进总体图；需要时用右侧子图单独展开。

## 2. 推荐工作流：从事实到可交付 SVG

按以下顺序工作。不要先画箭头，再回头猜结构或硬塞文字。

```text
官方配置 / 实现代码
        ↓
结构规格（JSON / 表格）
        ↓
画布、外框、色块与模块框布局
        ↓
主干 → 残差 → 分支 / 子图连线
        ↓
简短文字与关键尺寸
        ↓
自动检查 → SVG 预览 → 人工结构复核
```

### 第一步：确认事实边界

先确定本图想表达的层级：总体模型、一个 Decoder Block，还是 Attention / FFN / MoE 子图。然后从官方 `config.json` 和模型 `forward()` 收集事实；未能证实的模块、连线和层调度不要画。

### 第二步：写结构规格

把模型名、层数、隐藏维度、注意力类型、FFN / MoE 类型、重复层调度、关键路由参数和来源写成结构规格。图中的数字只能从该规格复制，不能手工凭记忆填写。

### 第三步：先布局框，再放文字

1. 先确定画布、中轴线、灰色外框和有色 Decoder Block；
2. 让有色 Block 以主干为中心，左右在灰色外框内保留均衡留白；需要更大空间时，优先加宽背景框或画布；
3. 再放高度一致的白色模块框，按主干从下到上均匀排列；
4. 最后放文字。文字过长时，先删掉次要信息；仍需保留时，加宽或加高框体、拆成清晰的多行，绝不缩小到难以读或贴着边界。

### 第四步：按优先级连线

1. 先画竖直主干；
2. 再画侧向输入（如 RoPE）和输出；
3. 再画残差、分支和汇合；
4. 最后画子图之间的说明性连接。

每加一条线就确认它不穿过文字、深色模块或无关矩形。若主干与标签冲突，优先移动标签到留白区或重新分配纵向空间；不要把主干绕成不必要的折线。

### 第五步：每次修改都检查

每一次 SVG 修改后都运行检查器。检查通过后仍需预览 SVG：自动检查保证几何底线，人工复核保证视觉层级和模型含义正确。

## 3. 结构事实必须有来源

### 3.1 优先级

按可信度从高到低使用：

1. Hugging Face 模型仓库的 `config.json`；
2. 官方模型实现代码（例如 Transformers 中的 `modeling_*.py`）；
3. 官方技术报告或模型卡；
4. 可信的推理实现；
5. 二手文章或已有示意图，仅用于辅助理解，不能作为唯一依据。

### 3.2 `config.json` 能确认什么

配置通常能确认：

- 模型类别和架构名，例如 `Qwen3ForCausalLM`；
- `hidden_size`、`num_hidden_layers`；
- `num_attention_heads`、`num_key_value_heads`；
- `intermediate_size`、激活函数；
- `vocab_size`、最大位置长度、RoPE 参数；
- 是否共享输入嵌入和输出头；
- MoE 的专家数量、top-k、路由策略（如果配置提供）。

配置不能完整确认模块执行顺序、投影层连接方式、残差位置或混合注意力调度。对此必须查看模型实现。

### 3.3 从模型实现确认模块树

以实际 Python 类为准，逐层读取：

```text
Qwen3ForCausalLM
└── model: Qwen3Model
    ├── embed_tokens
    ├── layers: ModuleList[Qwen3DecoderLayer] × N
    │   ├── input_layernorm
    │   ├── self_attn
    │   ├── post_attention_layernorm
    │   └── mlp
    └── norm
└── lm_head
```

随后阅读 `forward()`，确定真实数据流：

- Norm 是 Attention / FFN 之前还是之后；
- 残差在哪一步相加；
- Attention 是标准因果注意力、GQA、MLA、稀疏注意力还是线性注意力；
- FFN 是普通 MLP、SwiGLU、MoE，还是并行 / 串行专家设计；
- 不同层是否交替使用不同 mixer 或注意力机制。

只有类定义和 `forward()` 都能对上时，才可以把模块和箭头画进图中。

## 4. 先写“结构规格”，再画 SVG

不要直接凭记忆修改 SVG。先将每个模型整理成结构规格（JSON 或表格），至少包含：

```json
{
  "architecture": "Qwen3ForCausalLM",
  "layers": 36,
  "hidden_size": 2560,
  "attention": {
    "type": "causal grouped-query attention",
    "num_heads": 32,
    "num_kv_heads": 8,
    "head_dim": 128,
    "position_encoding": "RoPE"
  },
  "ffn": {
    "type": "SwiGLU",
    "intermediate_size": 9728
  },
  "norm": "RMSNorm",
  "tie_word_embeddings": true
}
```

结构规格是图的唯一数据来源。SVG 中的文字、重复次数与尺寸都从它填写，避免配置更新后图和事实脱节。

## 5. 总体图的正确画法

### 5.1 主干

采用自下而上的单一主干：

```text
Tokenized text → Token embedding → Decoder Block × N → Final Norm → LM Head → logits
```

- 主干箭头保持竖直，只有确实需要绕开模块时才折线；
- Tokenized text 放在模型外框下方，不与灰色模型外框重叠；
- 顶部输出箭头应伸出灰色外框；
- Decoder Block 用有色圆角大框表示，并明确标示重复 `N ×`；
- 外框左右留白对称，Block 不要贴着灰色外框。
- 配置来源、仓库路径等溯源信息默认保存在结构规格、SVG 的 `desc` 或交付说明中；除非用户明确需要，不在图内添加 `Source: ...` 这类占空间的文字。

### 5.2 Decoder Block

典型 pre-norm decoder 的阅读方向应为：

```text
输入
  → RMSNorm 1 → Attention → ⊕
  → RMSNorm 2 → FFN / MoE → ⊕
  → 输出
```

- 两个残差路径画在主要模块右侧；
- 残差箭头必须在加法圆 `⊕` 的边界处结束，而不是穿入圆心；
- 残差线不要穿过 Attention、FFN / MoE 的深色模块框；
- Block 纵向空间要足够，白色框的高度统一，框与框之间保留稳定间距。

不同模型若是 post-norm、并行 Attention+MLP 或具有 mixer 交替层，必须按真实 `forward()` 画，不能套用上图。

### 5.3 RoPE 与旁路输入

- RoPE 应连接到 Attention，而不是 Token Embedding 或残差线；
- 若使用侧向箭头，优先与 Attention 内无文字的区域同高，画成一条水平线；
- 箭头不能横穿 Attention 内的文字。

## 6. 关键子模块的正确画法

### 6.1 GQA / MHA / MLA

总体图只需标出实际注意力类型，例如：

- `Masked multi-head attention`；
- `Causal grouped-query attention`，并写出 Q heads / KV heads；
- `Multi-head latent attention (MLA)`；
- `Linear attention + full attention`，并说明其层级或调度规则。

只有在有可靠实现依据时，才展开 Q/K/V 投影、latent 压缩或稀疏路由细节。

### 6.2 SwiGLU FFN

正确的数据流是：

```text
hidden states
 ├→ gate_proj → SiLU ─┐
 └→ up_proj ─────────┼→ element-wise multiply → down_proj
                      └────────────────────────────────────
```

- `gate_proj` 和 `up_proj` 从同一 hidden states 分叉；
- 只有 gate 分支经过 SiLU；
- 两条分支在乘法圆 `×` 汇合；
- 乘法之后才进入 `down_proj`；
- 分支、乘法圆与 `down_proj` 要垂直对齐。

### 6.3 MoE

最简 MoE 图应表达：

```text
输入 → Router → 被选中的若干 Expert FFN → 加权合并 → 输出
```

若模型有 shared expert、top-k、专家并行或负载均衡，只在有足够空间时作为旁注补充。专家编号或省略号不能压住箭头或专家框边界。

若模型采用“前若干层 Dense FFN、后续层 MoE”的混合层调度，Decoder Block 内应将 `FFN` 放在上方、`MoE` 放在下方，并用简短层范围标注区分（例如 `first 3 layers` 与 `next 75 layers`）。二者是不同层类型，不是同一层的串行算子：主干只能经过当前代表的层类型，另一种类型作为布局说明展示，不能画出误导性的串行数据箭头。

## 7. SVG 布局规范

### 7.1 框和留白

- 同类白色模块框使用固定高度；
- 竖向相邻且水平对齐的模块框之间至少保留 `32px`；
- 文字的估算边界不能触及矩形描边；
- 方框内的文字必须保留足够内边距，不能显得拥挤；优先精简为模块名和一项核心信息。若仍需多行说明，应增加方框高度，而不是缩小字体或把文字贴近边界；
- 深色模块也和白色模块一样必须参与文字边界检查，不能因配色不同而漏检；
- 有色 Block 应围绕内部主干和模块居中；左右留白不均或过窄时，扩大背景框而不是把内部模块挤在一起；
- 大色块内部上下留白要明显，不能让最上或最下模块贴边；
- 外框、色块和旁路的线宽保持一致的层级：外框略粗、普通连线略细、箭头清楚但不喧宾夺主。

### 7.2 文字

- 文字居中时使用 `text-anchor="middle"`；右对齐说明使用 `text-anchor="end"`；
- 文本基线要落在白框的视觉中心；
- 文本不得相互重叠，不得与箭头、折线或矩形边界重叠；
- 同一列的多行文字即使尚未重叠，也要保留最小行间距；本项目 SVG 检查器默认要求至少 `6px`，避免出现视觉上粘连的文字；
- 较长的尺寸说明优先移到框外的空白区，而不是缩小到难以阅读；
- 不要为了避线随意移动文字，优先调整连线路由或扩大画布。

### 7.3 箭头

- 数据流箭头方向统一为自下而上；
- 普通直连优先使用直线；
- 箭头进入矩形时应正对目标框对应边的中点；侧向输入指向左 / 右边中点，上下主干指向上 / 下边中点。不要让箭头斜插到角落或只擦过矩形边缘；
- 只有残差、分支、跨模块连接使用折线；
- 折线的拐点应位于留白区，不能紧贴模块、圆节点或文字；
- 箭头端点进入矩形或圆节点时，停在描边附近，不能画过头；
- 残差箭头应连接到加法圆 `⊕` 的圆周，而非穿入圆心；残差起点与模块、圆节点保留可见间隙；
- 没有方向语义的汇合连线可使用无箭头直线。

## 8. 自动检查与人工复核

项目中的检查器是：

[`scripts/check_svg_arrow_connections.py`](../scripts/check_svg_arrow_connections.py)

每次新建或修改 SVG 后运行：

```bash
python3 scripts/check_svg_arrow_connections.py path/to/diagram.svg
```

它会检查：

- 指向残差加法圆的箭头是否穿进圆内；
- 纵向堆叠的模型框间距是否小于 `32px`；
- 文字之间是否重叠；
- 同一列文字之间是否过于拥挤；
- 文字是否与连接线 / 箭头相交；
- 文字是否触碰可见矩形框的边界。

其中“可见矩形框”包含外框、色块、普通模块、Attention、Router、MoE 和虚线子图面板；不能因为新增一种深色模块就绕过检查。

检查器依据 SVG 的 CSS 字号估算文字范围，因此适合拦截碰撞和拥挤，但不能判断模型语义，也不能可靠判断一条箭头是否应该进入某个模块的中点。这两项必须在视觉复核中逐条确认。

检查通过不等于图一定好看。因此还要在浏览器或 SVG 预览器中人工复核：

1. 从远处看，主干和 Block 是否一眼可读；
2. 从近处看，箭头是否指向正确模块、圆节点和边界；
3. 检查每条进入矩形的箭头是否对准对应边的中点，而不是角落或边缘；
4. 逐项对照结构规格，确认模型名、层数、尺寸和模块类型；
5. 确认没有为“排版好看”而画出实现中不存在的模块或连接。

## 9. 交付前清单

- [ ] 配置、实现代码与图中结构一致；
- [ ] 总体数据流、每个残差、每个分支方向正确；
- [ ] Attention、FFN / MoE、Norm 的顺序来自真实 `forward()`；
- [ ] 关键维度、层数、头数来自结构规格；
- [ ] 文字、线条、矩形无碰撞；
- [ ] 框内文字有足够留白；多行内容已通过加高框体而非压缩字体处理；
- [ ] 每条输入 / 输出箭头正对目标矩形边的中点；
- [ ] 残差箭头止于 `⊕` 圆周，未穿入圆内；
- [ ] 有色 Block 居中，内部模块与外框左右、上下留白合理；
- [ ] SVG 检查脚本通过；
- [ ] 已进行一次视觉预览。
